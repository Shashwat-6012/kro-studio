# KRO Studio

## Product Requirements, Architecture, and Implementation Blueprint

**Document status:** Initial product specification\
**Project name:** KRO Studio\
**Project type:** Open-source, UI-first Kubernetes application\
**Primary domain:** Kube Resource Orchestrator (KRO),
ResourceGraphDefinitions (RGDs), and RGD-defined custom resource
instances\
**Suggested license:** Apache License 2.0\
**Initial release target:** MVP / v0.1.0\
**Audience:** Open-source contributors, Kubernetes platform engineers,
developers, and project maintainers

------------------------------------------------------------------------

## 1. Executive Summary

KRO Studio is a web-based application for creating, inspecting,
updating, and managing KRO ResourceGraphDefinitions (RGDs), as well as
creating and managing the custom resource instances exposed by those
RGDs.

KRO lets platform engineers define reusable, Kubernetes-native APIs that
compose multiple underlying resources into a single higher-level
resource. KRO validates an RGD, generates a CustomResourceDefinition
(CRD) from its schema, and reconciles instances of that generated API
into the resources described by the RGD.

KRO Studio aims to make these workflows accessible through a graphical
interface instead of requiring users to author every manifest manually
and switch repeatedly between YAML, `kubectl`, and cluster inspection
tools.

The product has two core areas:

1.  **RGD Studio:** Discover, create, inspect, edit, validate, and
    manage ResourceGraphDefinitions.
2.  **Instance Manager:** Discover the APIs generated by RGDs, create
    instances through schema-aware forms, inspect instance status and
    composed resources, update instance specifications, and delete
    instances with appropriate safeguards.

The application is a management interface for KRO, not a replacement for
the KRO controller or the Kubernetes API. KRO remains responsible for
validating and reconciling RGDs and their instances.

### Critical Kubernetes scope clarification

**A KRO `ResourceGraphDefinition` is a cluster-scoped Kubernetes
resource; it does not belong to a Kubernetes namespace.** KRO's API
reference identifies `ResourceGraphDefinition` as cluster-scoped.

KRO Studio can offer a namespace-oriented workspace, filter namespaced
instances by namespace, and associate RGDs with a logical team or
workspace using labels. However, it must not represent an RGD as if it
were natively namespaced.

The UI must clearly distinguish:

-   **Cluster-scoped RGDs:** Cluster-level definitions managed through
    cluster-scoped permissions.
-   **Generated custom resource definitions (CRDs):** Cluster-level API
    definitions created by KRO.
-   **Custom resource instances:** Namespaced or cluster-scoped
    according to the scope configured in the RGD's schema.
-   **Composed resources:** Kubernetes resources created and managed by
    KRO for each instance.

If a user selects a namespace, KRO Studio should use it as the default
workspace/filter for namespaced instances and as a contextual label for
the workflow---not as the actual namespace of an RGD.

## 2. Problem Statement

KRO provides a Kubernetes-native way to define reusable APIs that group
related resources and express dependencies between them. However, users
who work with KRO must understand RGD manifests, generated schemas,
Kubernetes API discovery, instance manifests, reconciliation status, and
the resources created by each instance.

Common usability challenges include:

-   Authoring and maintaining RGD YAML can be difficult for users who
    are not comfortable with complex Kubernetes manifests and CEL
    expressions.
-   Users need to inspect the RGD definition, its schema, its validation
    conditions, and its generated API in different places or commands.
-   Creating instances requires knowledge of the generated API, required
    fields, types, defaults, and permitted values.
-   A user may create an instance but still need to inspect the
    instance's conditions and the underlying Kubernetes resources to
    understand whether it is healthy.
-   The relationship between an RGD, its generated CRD, its instances,
    and the resources composed by those instances is not always easy to
    understand from a single view.
-   Editing or deleting an RGD or instance is potentially consequential.
    Users need clear feedback and deliberate confirmation before
    destructive actions.
-   Cluster RBAC can allow access to some resources but deny access to
    others. A UI must present permission errors clearly instead of
    making incomplete information appear to be a successful result.

KRO Studio addresses these challenges with a single UI for the RGD and
instance lifecycle, using the Kubernetes API and KRO's existing
reconciliation behavior.

### Problem statement

> Kubernetes users need a clear, safe, and discoverable way to author
> and manage KRO ResourceGraphDefinitions and the custom resource
> instances they expose. KRO Studio provides a UI-first management
> experience while preserving Kubernetes RBAC, KRO reconciliation, and
> Kubernetes-native resource semantics.

## 3. Vision and Goals

### Vision

Make KRO-based APIs easier to author and operate by providing a focused,
Kubernetes-native graphical workspace for definitions and their
instances.

### Goals

1.  Provide a discoverable inventory of RGDs and their
    readiness/validation status.
2.  Allow authorized users to create, inspect, edit, validate, and
    delete RGDs through the UI.
3.  Explain the API schema exposed by each RGD.
4.  Discover generated custom resource APIs dynamically instead of
    hardcoding resource kinds.
5.  Generate instance creation forms from the schema available in the
    Kubernetes API.
6.  Allow users to list, inspect, update, and delete custom resource
    instances.
7.  Show the composed resources owned or managed by an instance and
    their current status.
8.  Surface Kubernetes and KRO errors, conditions, and events with
    actionable context.
9.  Respect Kubernetes authentication and RBAC; do not silently bypass
    cluster permissions.
10. Deliver a UI-first application. Users must not need a KRO Studio CLI
    to complete supported workflows.

### Non-goals

The initial product is not intended to:

-   Replace KRO, Kubernetes, `kubectl`, or the Kubernetes API.
-   Replace Argo CD, Flux, or another GitOps controller.
-   Become a general-purpose Kubernetes dashboard.
-   Manage every type of Kubernetes resource unrelated to KRO.
-   Implement a new reconciliation engine.
-   Guarantee that a static RGD preview exactly reproduces all live KRO
    behavior.
-   Automatically remediate all unhealthy child resources.
-   Implement a full multi-cluster control plane in the MVP.
-   Provide a hosted SaaS service or central account system in the MVP.
-   Add AI-generated manifests or an AI agent in the MVP.
-   Provide a command-line interface as a primary or required user
    interface.

## 5. Product Scope

### 5.1 MVP scope: RGD management

The application must support:

-   Listing and searching RGDs.
-   Viewing RGD metadata, specification, schema, resources, and status
    conditions.
-   Visualizing existing RGDs as a read-only resource dependency graph.
-   Creating an RGD through a guided UI.
-   Editing an existing RGD through a form and/or YAML editor.
-   Validating an RGD locally where possible and against the connected
    cluster where supported.
-   Applying or updating an RGD through the Kubernetes API after
    explicit user confirmation.
-   Showing KRO's observed reconciliation/validation result after
    submission.
-   Deleting an RGD with a clear warning and explicit confirmation.
-   Displaying generated CRD information when discoverable.
-   Explaining API discovery or permission failures.

### 5.2 MVP scope: RGD-defined instance management

The application must support:

-   Discovering the custom resource API associated with an RGD.
-   Listing instances, filtered by namespace when the generated API is
    namespaced.
-   Starting instance creation from an RGD once its generated API is
    established and discoverable, using a schema-aware form.
-   Offering a YAML editor or advanced manifest mode for fields that
    cannot be represented cleanly in a form.
-   Editing an instance specification.
-   Viewing metadata, specification, status, conditions, and relevant
    events.
-   Viewing child/composed resources associated with an instance when
    discoverable and permitted.
-   Navigating from an instance to its RGD and from an RGD to its
    instances.
-   Deleting an instance with a clear warning and explicit confirmation.
-   Showing asynchronous reconciliation status after
    create/update/delete operations.

### 5.3 MVP scope: operational UX

-   Namespace selector for namespaced instance workflows.
-   Cluster-scope indicator for RGDs and cluster-scoped generated APIs.
-   Loading, empty, error, and permission-denied states.
-   Refresh and reasonable polling for changing status.
-   Search and basic filters.
-   Dark and light theme support if feasible.
-   Responsive desktop-first layout.
-   Accessible forms, labels, keyboard navigation, and error messages.

### 5.4 Post-MVP possibilities

These are deliberately not requirements for v0.1.0:

-   Interactive drag-and-drop editor for creating and changing the DAG.
-   Multi-cluster management.
-   Git provider integration and pull-request workflows.
-   RGD revision history and semantic compatibility analysis.
-   RGD regression testing and reusable test cases.
-   Approval policies and role-specific workflows.
-   Audit history beyond Kubernetes events and application logs.
-   Bulk operations.
-   Import/export of RGD templates and curated examples.
-   Metrics, trends, and fleet-level dashboards.
-   Advanced policy engines.
-   AI-assisted authoring.

## 6. Product Principles

1.  **Kubernetes remains the source of truth.** KRO Studio reads and
    writes Kubernetes resources through supported APIs.
2.  **KRO remains the reconciler.** The application does not create or
    manage KRO's child resources independently.
3.  **No false namespace semantics.** RGDs are presented as
    cluster-scoped resources.
4.  **Safe by default.** Destructive or high-impact operations require
    explicit confirmation.
5.  **Dynamic discovery.** Do not hardcode every generated CRD or custom
    resource kind.
6.  **Transparent status.** Distinguish the result of an API write from
    the eventual result of KRO reconciliation.
7.  **Respect RBAC.** The UI must not claim that a user can perform an
    action unless the backend is authorized to do so.
8.  **Progressive disclosure.** Simple users get guided forms; advanced
    users can inspect or edit YAML.
9.  **No silent destructive behavior.** Never cascade-delete unrelated
    resources or bypass KRO lifecycle semantics.
10. **UI-first.** All MVP user workflows are available through the web
    interface.

## 7. Core User Journeys

### Journey A: Create an RGD

1.  User opens the RGDs page.
2.  User selects **Create RGD**.
3.  User chooses a creation path:
    -   Guided form / visual builder.
    -   YAML editor.
    -   Start from an example template.
4.  User enters metadata, API schema, and resource definitions.
5.  The UI checks basic structural validity and required fields.
6.  User reviews the generated manifest.
7.  User selects **Validate**.
8.  The application performs supported validation and clearly labels any
    checks it cannot perform.
9.  User reviews warnings and errors.
10. User selects **Create RGD** and confirms the operation.
11. The backend submits the resource to Kubernetes.
12. The UI shows the API write result and then watches or polls for KRO
    conditions.
13. The RGD detail page shows whether KRO has accepted and reconciled
    the definition.
14. The generated API becomes available when the Kubernetes API reports
    it as established/discoverable.

### Journey B: Inspect and edit an RGD

1.  User opens the RGD catalog.
2.  User searches or filters for an RGD.
3.  User opens its detail page.
4.  User inspects schema, resources, conditions, and generated API
    details.
5.  User selects **Edit**.
6.  The UI loads the latest object and its resource version.
7.  User makes changes in the form or YAML editor.
8.  The UI validates and displays the proposed changes.
9.  User confirms the update.
10. The backend updates the resource using conflict-aware API semantics.
11. The UI displays the updated object and subsequent KRO status.
12. If the update conflicts with a newer version, the UI asks the user
    to reload and reconcile the change instead of overwriting silently.

### Journey C: Create an instance

1.  User opens an RGD detail page.
2.  User selects **Create instance**.
3.  The UI discovers the generated CRD and determines its scope.
4.  For a namespaced API, the user selects a namespace.
5.  The UI builds a form from the generated CRD's OpenAPI schema.
6.  Required fields, defaults, enums, bounds, arrays, and objects are
    rendered where supported.
7.  User reviews the generated manifest.
8.  User submits the form.
9.  The backend creates the custom resource through the Kubernetes API.
10. The UI shows the API write result and follows instance status.
11. The instance detail page displays conditions and discovered composed
    resources.

### Journey D: Inspect an instance and its composed resources

1.  User opens an instance from the global instance list or an RGD
    detail page.
2.  The application shows identity, namespace/scope, age, spec, status,
    and conditions.
3.  The application discovers likely composed resources using reliable
    ownership references, labels, or KRO-supported metadata.
4.  Each child resource shows kind, name, namespace, and status when
    accessible.
5.  User opens a child resource to inspect a read-only summary and,
    where allowed, its YAML.
6.  Permission errors or missing resources are shown explicitly.
7.  The UI distinguishes an absent child, a child that is terminating,
    and a child that the user is not authorized to inspect.

### Journey E: Delete an instance

1.  User selects **Delete instance**.
2.  The UI explains that KRO may delete resources managed by that
    instance according to Kubernetes and KRO lifecycle behavior.
3.  The UI shows the exact instance identity and namespace/scope.
4.  User explicitly confirms.
5.  The backend submits the deletion request.
6.  The UI shows a terminating state until deletion is observed or a
    clear error occurs.
7.  The application does not manually delete child resources to simulate
    KRO cleanup.

### Journey F: Delete an RGD

1.  User selects **Delete RGD**.
2.  The UI displays a high-impact warning.
3.  The UI explains that the generated CRD and existing instances may be
    affected and that exact consequences depend on KRO behavior,
    Kubernetes deletion semantics, and the installed KRO version.
4.  The application checks what it can discover and presents a
    best-effort impact summary.
5.  User must explicitly confirm the exact RGD name.
6.  The backend submits the delete request only if authorized.
7.  The UI tracks the resulting state and presents any failures or
    remaining resources.
8.  If impact cannot be determined reliably, the UI must say so rather
    than imply the operation is safe.

## 9. RGD and Instance Lifecycle Semantics

This section is important because KRO Studio must not confuse a
successful Kubernetes API write with a successfully reconciled
application.

### RGD lifecycle presentation

The UI should present the following as distinct states, derived from the
installed KRO version and actual resource conditions:

-   **Submitting:** The UI is sending the API request.
-   **Accepted by API:** Kubernetes accepted the write request.
-   **Reconciling / Pending:** KRO has not yet reported a final ready
    state.
-   **Ready / Validated:** The relevant KRO conditions indicate
    successful processing.
-   **Error / Invalid:** KRO reports a validation or reconciliation
    failure.
-   **Unknown:** The UI cannot confidently classify the state.
-   **Deleting / Terminating:** Deletion has been requested but the
    resource remains present.

These are UI-level classifications, not a claim that every KRO version
exposes exactly these condition names. Map real condition types and
reasons into the UI while preserving the raw condition details.

### Instance lifecycle presentation

The UI should distinguish:

-   Pending creation.
-   Reconciling.
-   Ready.
-   Degraded or failed.
-   Deleting/terminating.
-   Unknown or inaccessible.

Use instance status conditions and child resource status where
available. Do not infer that an instance is healthy solely because the
API request succeeded.

### Deletion semantics

-   Deleting an instance asks Kubernetes/KRO to perform its normal
    lifecycle behavior.
-   Deleting an RGD is a high-impact operation and may affect the
    generated API and existing instances.
-   Exact behavior may vary by KRO version and Kubernetes lifecycle
    semantics.
-   KRO Studio must not promise that all composed resources will be
    preserved or deleted unless that behavior is verified for the
    supported configuration.
-   If the application cannot determine the impact, it must present that
    uncertainty explicitly.
-   Do not implement a custom recursive delete of child resources as a
    substitute for KRO's controller.

### 10.1 Main navigation

Suggested left navigation:

-   Overview
-   ResourceGraphDefinitions
-   Instances
-   Connection / Settings
-   About

Keep the interface focused. Do not add generic Kubernetes resource
management pages unrelated to RGDs and their instances in the MVP.

### 10.2 Overview page

Display:

-   Kubernetes connection state.
-   KRO installation/capability status where detectable.
-   Number of discovered RGDs.
-   Number of discoverable instances.
-   RGD condition summary.
-   Recent relevant events, if available and authorized.
-   Helpful empty states with links to create an RGD or inspect an
    existing one.

Do not make the Overview page a substitute for the detailed RGD and
Instance pages.

### 10.3 RGD catalog page

Suggested columns:

-   Name
-   API kind / group
-   Generated kind
-   Readiness/validation status
-   Instance count, if discoverable
-   Age
-   Labels
-   Actions

Filters:

-   Search by name.
-   Condition/health state.
-   Label.
-   Generated API availability.

Because RGDs are cluster-scoped, do not imply that changing the
namespace selector changes which namespace owns an RGD.

### 10.4 RGD detail page

Suggested tabs:

1.  **Overview:** Metadata, status, conditions, API identity,
    timestamps.
2.  **Schema:** Generated API inputs, required fields, types, defaults,
    and constraints.
3.  **Resources:** Resources and dependencies declared by the RGD, with
    both a list and read-only graph view.
4.  **Instances:** Instances associated with the generated API.
5.  **YAML:** Full manifest with copy support and edit action.
6.  **Events / Conditions:** Relevant condition messages and events,
    when available.

### 10.5 RGD creation/edit page

Provide two editing modes:

-   **Guided editor:** Metadata, schema, resource definitions, and
    dependencies.
-   **YAML editor:** Advanced users can inspect or edit the full
    manifest.

Requirements:

-   Always show the resulting YAML before submission.
-   Clearly indicate required fields.
-   Validate obvious structural issues before sending.
-   Show server-side errors beside the relevant field when mapping is
    reliable.
-   Preserve unknown fields when editing existing resources; do not
    silently drop fields the editor does not understand.
-   Avoid a form-only implementation that prevents users from using
    valid KRO features not yet supported by the visual builder.

### 10.6 Instance list page

Suggested columns:

-   Instance name
-   Generated kind
-   Namespace (or a cluster-scope indicator)
-   Associated RGD
-   Status
-   Age
-   Actions

Filters:

-   Namespace for namespaced instances.
-   RGD / generated kind.
-   Status.
-   Search by name.

### 10.7 Instance creation page

-   Build form controls from the generated CRD schema.
-   Use a namespace selector only for namespaced custom resources.
-   Use defaults and enum values from schema when available.
-   Support nested objects and arrays where practical.
-   Offer YAML mode for unsupported schema constructs.
-   Preview the final manifest.
-   Explain API validation errors and permissions failures.
-   Show progress after creation.

### 10.8 Instance detail page

Suggested sections:

-   Overview and health.
-   Spec.
-   Status and conditions.
-   Composed resources.
-   Events.
-   YAML.

The composed-resource panel should be read-only in the MVP, except for
navigation to details. KRO Studio must not compete with KRO by directly
managing child-resource lifecycle.

### 10.9 Design guidelines

-   Desktop-first but responsive.
-   Clear information hierarchy and compact technical tables.
-   Accessible colors; status must not rely on color alone.
-   Explicit confirmation dialogs for destructive actions.
-   Copy YAML / copy resource identity actions.
-   Empty states should explain the next useful action.
-   Keep raw Kubernetes error details available behind a readable
    summary.
-   Use stable URLs for detail pages so users can share navigation links
    within their authorized environment.

## 11. Technical Architecture

### 11.1 Chosen MVP stack

The MVP uses a **React UI and an ASP.NET Core Minimal API in one
deployable application and one Docker image**. ASP.NET Core serves the
compiled React files and handles the UI's `/api/*` requests. The browser
does not call the Kubernetes API directly.

**UI**

- React and TypeScript
- Vite for development and production bundling
- Accessible component library selected during UI implementation
- Schema-driven instance forms, with a YAML editor fallback

**Application/backend**

- .NET 10 LTS, using ASP.NET Core Minimal APIs; reassess the supported
  runtime before each major release
- Kubernetes official .NET client (`KubernetesClient`)
- Kubernetes API discovery and dynamic/custom-resource operations
- Structured logging with sensitive values redacted

**Packaging and deployment**

- Multi-stage Docker build: build the React UI, publish the .NET app,
  then copy both into a small runtime image
- One process and one origin for the UI and app API
- Local-first MVP; container access to a user-provided kubeconfig
- Public source repository and tagged releases on GitHub
- Public container images in GitHub Container Registry (GHCR)
- Helm deployment may follow after local installation and security
  behavior are proven

The .NET Kubernetes client is listed among Kubernetes' officially
supported client libraries. The exact .NET and client-library versions
must be pinned and checked against the Kubernetes versions KRO Studio
chooses to support. [Kubernetes client libraries](https://kubernetes.io/docs/reference/using-api/client-libraries/)

This decision supersedes the earlier Go backend recommendation. Keep
the UI and server in one repository and one release pipeline; they are
separate source projects but ship together.

### 11.2 Why a backend is recommended

The browser should not receive a kubeconfig, client certificate, bearer
token, or other long-lived cluster credential.

A backend provides one place to:

-   Authenticate UI users.
-   Enforce application-level permissions.
-   Use in-cluster service account credentials.
-   Call Kubernetes APIs.
-   Handle dynamic API discovery.
-   Normalize Kubernetes errors.
-   Keep credentials and cluster access out of browser JavaScript.

For local-first operation, the backend uses a user-provided kubeconfig
and the Kubernetes identity selected by that configuration. Mount or
provide the file at runtime; never bake credentials into an image or
frontend bundle. Bind the local service to loopback by default. A future
in-cluster mode can use a dedicated service account with documented
least-privilege RBAC, but it must define how application users are
authenticated and authorized before it is exposed to a team.

``` text
| RGD service | Discovery service | Instance service  |
| Validation | Error mapping | Status polling          |
+---------------------------+--------------------------+
                            |
                            | Kubernetes API
                            v
+------------------------------------------------------+
|                  Kubernetes API Server               |
|                                                      |
| RGDs (cluster-scoped)                                |
| Generated CRDs (cluster-scoped)                      |
| RGD-defined custom resource instances                |
| Composed resources                                    |
+---------------------------+--------------------------+
                            |
                            v
+------------------------------------------------------+
|                   KRO Controller                     |
|                                                      |
| Validates RGDs, generates APIs, reconciles instances |
| and manages composed resources                       |
+------------------------------------------------------+
```

### 11.4 Core backend modules

-   **Cluster connection:** Establish and monitor Kubernetes
    connectivity.
-   **Discovery:** Discover API groups, versions, resources, scopes, and
    CRDs dynamically.
-   **RGD service:** List, get, create, update, validate where
    supported, and delete RGDs.
-   **Generated API service:** Resolve an RGD to the relevant generated
    CRD and API resource.
-   **Instance service:** List, get, create, update, and delete
    generated custom resource instances.
-   **Composition inspector:** Discover resources associated with an
    instance using reliable owner references or supported KRO metadata.
-   **Status service:** Map raw conditions to UI-friendly states without
    discarding source details.
-   **Authorization/error service:** Normalize forbidden, conflict,
    unavailable, timeout, and validation responses.
-   **Audit/logging:** Record application-initiated actions without
    logging secrets or sensitive manifest values unnecessarily.

### 11.5 Dynamic discovery

KRO Studio must not assume every RGD produces the same custom resource
kind or plural name.

For each RGD:

1.  Read the RGD.
2.  Inspect the RGD schema and relevant KRO metadata.
3.  Discover the generated CRD through the Kubernetes API where
    possible.
4.  Read its group, versions, kind, plural, and scope.
5.  Wait for the CRD to be established and discoverable before enabling
    instance creation.
6.  Use API discovery/REST mapping to resolve the correct endpoint.
7.  Handle a missing, not-yet-established, or inaccessible CRD
    explicitly.

Do not rely exclusively on name conventions to resolve a generated API.

### 11.6 Composed resource discovery

Preferred discovery order:

1.  Kubernetes owner references where KRO provides them reliably.
2.  KRO-supported labels/annotations or metadata documented for the
    supported version.
3.  Explicit references in the instance status or other documented API
    fields, if available.

Do not associate resources solely because their names look similar. If a
reliable relationship cannot be established, show that the resource list
is incomplete or unavailable.

## 12. API Design for the KRO Studio Backend

These are proposed application endpoints, not Kubernetes API paths. The
backend should call the actual Kubernetes API internally.

Use `/api/v1` as the initial prefix.

### 12.1 Connection and capability

  ------------------------------------------------------------------------
  Method                  Endpoint                 Purpose
  ----------------------- ------------------------ -----------------------
  GET                     `/api/v1/healthz`        Application health

  GET                     `/api/v1/connection`     Kubernetes connectivity
                                                   and active cluster
                                                   identity

  GET                     `/api/v1/capabilities`   Detect KRO, relevant
                                                   CRDs, API versions, and
                                                   supported UI features
  ------------------------------------------------------------------------

Do not expose credentials in connection responses.

### 12.2 RGD endpoints

  ---------------------------------------------------------------------------------
  Method                  Endpoint                          Purpose
  ----------------------- --------------------------------- -----------------------
  GET                     `/api/v1/rgds`                    List RGDs

  POST                    `/api/v1/rgds`                    Create an RGD

  GET                     `/api/v1/rgds/{name}`             Get an RGD

  PUT or PATCH            `/api/v1/rgds/{name}`             Update an RGD

  DELETE                  `/api/v1/rgds/{name}`             Request RGD deletion

  POST                    `/api/v1/rgds/validate`           Validate a proposed
                                                            manifest using
                                                            supported checks

  GET                     `/api/v1/rgds/{name}/api`         Resolve generated
                                                            CRD/API information

  GET                     `/api/v1/rgds/{name}/instances`   List instances for the
                                                            RGD's generated API
  ---------------------------------------------------------------------------------

Implementation note: route ordering must ensure `/rgds/validate` is
matched before `/rgds/{name}`. Alternatively, use a separate
`/validation/rgd` path.

### 12.3 Instance endpoints

Use a stable internal identifier for the resolved API resource rather
than assuming the generated kind is globally unique.

  ---------------------------------------------------------------------------------------------------------------
  Method                  Endpoint                                                        Purpose
  ----------------------- --------------------------------------------------------------- -----------------------
  GET                     `/api/v1/apis`                                                  List discovered
                                                                                          RGD-defined APIs

  GET                     `/api/v1/apis/{apiId}/instances`                                List instances for a
                                                                                          resolved API

  POST                    `/api/v1/apis/{apiId}/instances`                                Create an instance

  GET                     `/api/v1/apis/{apiId}/instances/{namespace}/{name}`             Get a namespaced
                                                                                          instance

  PATCH                   `/api/v1/apis/{apiId}/instances/{namespace}/{name}`             Update a namespaced
                                                                                          instance

  DELETE                  `/api/v1/apis/{apiId}/instances/{namespace}/{name}`             Delete a namespaced
                                                                                          instance

  GET                     `/api/v1/apis/{apiId}/instances/{namespace}/{name}/resources`   Inspect associated
                                                                                          resources
  ---------------------------------------------------------------------------------------------------------------

For cluster-scoped instances, use a separate route shape that omits
namespace. The implementation must resolve and verify resource scope
before constructing a Kubernetes API request. URL encoding and
identifier validation are required.

### 12.4 API behavior

-   Use standard HTTP status codes.
-   Return structured errors with a stable application error code, a
    readable message, and optional field-level details.
-   Do not return raw credentials or sensitive request headers.
-   Preserve Kubernetes status/reason/message information when safe.
-   Support pagination for potentially large lists.
-   Use Kubernetes `resourceVersion` or equivalent concurrency controls
    to avoid silent overwrites.
-   Treat create/update responses as API-write results, not proof of
    successful KRO reconciliation.
-   Use bounded timeouts and cancel Kubernetes requests when the client
    disconnects.
-   Use server-side watches or controlled polling where appropriate; do
    not poll every resource excessively.

## 13. Data and State Management

Kubernetes is the source of truth for RGDs, generated CRDs, instances,
and composed resources.

The MVP should avoid introducing a separate database unless a concrete
feature requires persistent application-owned data.

### Data held by Kubernetes

-   RGD specs and status.
-   Generated CRDs and their schemas.
-   Custom resource instances.
-   Composed resources.
-   Conditions, events, and Kubernetes metadata.

### Application-transient data

-   Current search/filter values.
-   Unsaved editor contents.
-   Form state.
-   The active namespace filter.
-   Short-lived discovery results.
-   UI polling and loading state.

### Potential later persistent data

A database may become useful for user preferences, approval workflows,
or an application-level audit trail. It is not required for the first
release.

Do not store Kubernetes credentials or copies of sensitive manifests in
a database by default.

## 14. Security and RBAC

Security is a core product requirement because KRO Studio can create and
delete cluster-level definitions and resources.

### 14.1 Authentication

The deployment must define how users authenticate. Options may include:

-   An authenticated reverse proxy or platform identity provider.
-   An explicitly configured local development identity for
    non-production use.
-   A future integration with an existing Kubernetes platform's identity
    model.

Do not ship an internet-accessible UI with anonymous write access by
default.

### 14.2 Authorization

-   Kubernetes RBAC remains authoritative for API operations.
-   Use a least-privilege service account.
-   Separate read and write permissions where practical.
-   Explain that cluster-scoped RGD operations require cluster-scoped
    authorization.
-   Namespace-scoped permissions for instances do not automatically
    grant permission to manage RGDs.
-   Never bypass a Kubernetes `Forbidden` response by switching to a
    broader credential silently.
-   UI-level access controls are supplementary; backend and Kubernetes
    authorization must enforce actual permissions.

### 14.3 Safe write operations

-   Require explicit confirmation for deletion.
-   Show the exact resource identity and scope.
-   Use preflight/dry-run requests where supported and useful.
-   Handle update conflicts rather than overwriting a newer version
    silently.
-   Keep a clear distinction between a preview and an atomic guarantee.
-   Do not automatically delete composed resources.
-   Avoid granting wildcard write permissions across all API groups and
    resources unless a documented deployment mode genuinely requires
    them and the administrator explicitly accepts the risk.

### 14.4 Secret handling

RGDs or composed resources may contain references to Secrets. The UI
should avoid rendering Secret values unless there is a separately
justified, explicitly authorized requirement. Default behavior should
redact or summarize secret references rather than retrieve and display
secret payloads.

### 14.5 Security checklist

The detailed MVP authentication flows, Kubernetes permission matrix, and role-scope guidance are maintained in [Authentication and RBAC Design](authentication-and-rbac.md).

-   [ ] No kubeconfig or bearer token in frontend bundles.
-   [ ] No credentials in application logs.
-   [ ] Authentication is enabled/configured for shared deployments.
-   [ ] Kubernetes RBAC is documented and tested.
-   [ ] Delete and update permissions are enforced server-side.
-   [ ] Input validation and request-size limits are implemented.
-   [ ] Error responses do not expose stack traces or secrets.
-   [ ] Dependencies and container images are scanned in CI.
-   [ ] Security reporting instructions are published.

## 15. Error Handling and Edge Cases

The UI must handle at least the following conditions:

1.  Kubernetes API server is unreachable.
2.  KRO is not installed.
3.  The RGD CRD/API is missing.
4.  An RGD exists but is invalid or not ready.
5.  The generated CRD is not yet established.
6.  Discovery returns stale information after an RGD change.
7.  The user has read access but not write access.
8.  The user can read the RGD but cannot list its instances.
9.  The instance exists but some composed resources are inaccessible.
10. An update conflicts with a newer `resourceVersion`.
11. Deletion is blocked by finalizers or remains in a terminating state.
12. A KRO version exposes different conditions or capabilities.
13. The API schema includes a construct unsupported by the visual form
    renderer.
14. The generated API is cluster-scoped rather than namespaced.
15. An RGD deletion may have consequences that cannot be fully
    determined.
16. An API write succeeds but KRO reconciliation later fails.
17. A resource disappears between list and detail requests.
18. The API returns partial or incomplete information because of
    permissions.

The UI should use an **Unknown / Incomplete information** state when it
cannot safely classify an object. It must not label an object healthy
merely because an error could not be retrieved.

## 16. Compatibility Strategy

KRO APIs and capabilities may evolve. KRO Studio should:

-   Detect the installed KRO/API versions where possible.
-   Discover resources dynamically.
-   Avoid hardcoding generated API kinds.
-   Gate version-specific features based on capability detection.
-   Preserve raw YAML fields that the UI does not understand.
-   Keep version-specific condition mapping in a dedicated module.
-   Test against a declared supported KRO version range.
-   Document the minimum supported Kubernetes and KRO versions.
-   Fail clearly when a feature requires an unsupported API.

The project must choose and document its initial supported
KRO/Kubernetes versions before its first stable release. Do not claim
compatibility with every KRO version until it has been tested.

## 22. Open-Source Project Strategy

### Repository and licensing

-   Use a public GitHub repository as the canonical source repository.
-   Use the Apache-2.0 license, subject to confirming project ownership
    and contribution policy before the first public release.
-   Include a clear README, screenshots, architecture diagram,
    installation guide, and a short demo.
-   Publish supported KRO/Kubernetes versions.
-   Provide `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, and `SECURITY.md`.

### Free publishing and distribution plan

The initial distribution target is a self-hosted/local application,
not a hosted service. The following GitHub services provide a practical
starting point for a public open-source project. Provider pricing and
terms can change, so verify them before each release:

-   **Source, issues, and collaboration:** GitHub public repository.
-   **Versioned downloads and release notes:** GitHub Releases; attach
    source archives and, when useful, checksums and standalone
    deployment files.
-   **Container distribution:** GitHub Container Registry (GHCR), using
    a public package such as `ghcr.io/<owner>/kro-studio`. GitHub
    currently lists public packages as free and says Container Registry
    image storage and bandwidth are currently free. [GitHub Packages
    billing](https://docs.github.com/en/billing/concepts/product-billing/github-packages)
-   **Build and publish automation:** GitHub Actions. Usage is currently
    free for standard GitHub-hosted runners in public repositories,
    within the platform's limits and terms. [GitHub Actions
    billing](https://docs.github.com/en/actions/concepts/billing-and-usage)
-   **Documentation site:** GitHub Pages can host static project
    documentation, but it does not run the ASP.NET Core application.
    The application itself is distributed as a container.

Docker Hub may be offered as an additional image mirror, but it is not
the initial source of truth. Its free Personal tier has pull limits, so
GHCR is the default public image registry. [Docker Hub pull
limits](https://docs.docker.com/docker-hub/usage/pulls/)

An initial tagged release should publish a versioned image and a
`latest` tag, release notes, supported-version information, and clear
run instructions. Avoid promising permanently free hosting or unlimited
bandwidth: users run the image themselves, and registry policies are
provider-controlled.

### Contribution model

-   Label issues as `good first issue`, `help wanted`, `bug`, and
    `enhancement`.
-   Keep feature requests tied to the defined scope.
-   Require automated tests for API behavior and lifecycle changes.
-   Use pull requests and CI checks to protect the main branch.

### Adoption strategy

-   Start with a local Kind-based demo.
-   Publish a short video demonstrating the full UI workflow.
-   Ask KRO users and Kubernetes platform engineers to test the alpha.
-   Collect feedback about usability, safety, missing operations, and
    supported KRO versions.
-   Track real usage and issues, not just repository stars.

### Competitive context

The KRO ecosystem already has UI efforts, including `kro-ui` and a KRO
plugin for Headlamp. KRO Studio should not claim that no UI exists. Its
value proposition is a focused UI-first workflow for authoring and
managing RGDs and their instances.

Before implementation, evaluate existing projects and their current
capabilities. Consider contributing fixes upstream or integrating with
existing work where doing so helps the community.

## 25. Final Product Definition

**KRO Studio is an open-source, UI-first web application for authoring
and managing KRO ResourceGraphDefinitions and the custom resource
instances generated from them.**

It provides a focused interface for:

-   Discovering and inspecting RGDs.
-   Creating, validating, editing, and deleting RGDs.
-   Discovering the generated CRD and its schema.
-   Creating, inspecting, updating, and deleting RGD-defined instances.
-   Viewing status, conditions, and discoverable composed resources.
-   Preserving Kubernetes RBAC and KRO lifecycle behavior.

The first release should concentrate on one cluster and the two core
workflows: **RGD management** and **instance management**. It should not
attempt to become a general Kubernetes dashboard or replace KRO's
controller.

The product is successful when a developer can complete the entire
supported workflow through the UI, understand what KRO is doing, and
perform operations safely without needing a KRO Studio CLI.
